#+AUTHOR: 開発チーム

* 1. はじめに
本ドキュメントは、Rustを用いたフルスクラッチでのGUIテキストエディタ（wgpu + cosmic-text ベース）開発におけるコア・アーキテクチャ方針、発生し得る技術的課題への対策、および初期の開発ロードマップをまとめたものである。ZedやSublime Textに匹敵するモダンで超高速なエディタの実現を目標とする。

* 2. コア・アーキテクチャの全体像 (想定設計)
既存のGUIフレームワークに依存せず、OSからの生イベント処理、テキストレイアウト計算、GPUレンダリングのすべてを単一のパイプラインとして自前で設計・構築する。システムは大きく分けて以下の3つの独立したレイヤで構成される。

** 2.1. データ管理・操作層 (Text Core)
画面描画から完全に切り離された、純粋なテキストデータ構造。
- *Rope バッファ (ropey等)*: ファイルの全文字列を保持。行番号や文字インデックス（UTF-8/UTF-16）の相互変換を対数時間 $O(\log N)$ で行う心臓部。
- *Cursor / Selection 管理*: カーソルの位置（バイトオフセット、または行・列）や選択範囲を保持。

** 2.2. レイアウト・ラスタライズ層 (Layout Engine)
テキストデータを画面上のピクセル座標に変換する、最も計算負荷の高いレイヤ。
- *cosmic-text (Text System)*: フォント（TTF/OTF）を読み込み、現在のフォントサイズや1行の最大幅をもとに文字の配置（Shape処理）を行う。多言語混在行、絵文字幅、等幅（Monospace）のグリッド計算を一手に引き受ける。
- *Viewport（視体積）管理*: エディタ画面全体のサイズ（ピクセル）と、現在のスクロール位置（scroll_x, scroll_y）を管理。

** 2.3. GPU描画層 (Render Pipeline)
計算された位置に、実際に文字、カーソル、背景をピクセルとして描き出すレイヤ。
- *wgpu (GPU抽象化レイヤ)*: Vulkan / Metal / DirectX を抽象化したライブラリ。cosmic-text が生成した文字の画像（アトラス・テクスチャ）をGPUメモリに転送し、画面にポリゴン（四角形）として並べる。
- *wgpu による図形描画*: カーソル矩形、選択ハイライト、構文エラーの波線といった UI 要素は、Vello 等の外部ベクターグラフィックスライブラリを使わず、素の wgpu（クワッド描画）で実装する。シンプルな矩形・線分の描画には wgpu で十分であり、統合コストを最小に抑える。

* 3. メインループとイベント駆動の設計
winit を使用し、OSからのイベントを起点とする以下のパイプライン（Event Loop）を構築する。

#+BEGIN_EXAMPLE
[OSからのイベント（キー入力 / マウス移動 / ウィンドウサイズ変更）]
   │
   ▼
[状態の更新 (Update)]
   │ 1. キー入力を検知（例: 'A' が押された）
   │ 2. Text Core の `Rope` に文字挿入、カーソル位置を更新
   │ 3. スクロールが必要か判定（カーソルが画面外に出た場合）
   ▼
[レイアウト計算 (Layout)]
   │ 1. Viewport 内に見えている行（例: 20行目〜60行目）だけを特定
   │ 2. `cosmic-text` にその範囲のテキストだけを渡し、文字の配置を計算（クリッピング）
   │ 3. シンタックスハイライト（`syntect`等）の色情報を文字ごとに適用
   ▼
[描画命令の生成・発行 (Render)]
   │ 1. 背景色、カーソル（縦棒）の矩形描画命令を GPU に積む
   │ 2. `cosmic-text` のテクスチャアトラスから、文字のポリゴンを描画
   │ 3. `wgpu::Queue::submit` で一括してGPUへコマンドを送信 ───> 【画面更新】
#+END_EXAMPLE

* 4. 最適化の基本戦略
1. *画面外の徹底的なサボり (行単位のクリッピング)*
   100万行のファイルを開いていても、画面に表示されるのは高々50～100行である。現在のスクロール位置から「画面に映る最初の行と最後の行」をスライスとして切り出し、画面外のテキストに対するフォント計算、色付け、描画命令の生成を $O(1)$ で完全にスキップする。
2. *テクスチャアトラス (Font Caching)*
   文字（グリフ）を毎回ベクターからピクセルに変換すると重いため、一度描画した文字は GPU メモリ上の1枚の巨大な画像シート（テクスチャアトラス）にキャッシュする。2回目以降の描画はGPU内で画像の一部をコピーして並べるだけにする（cosmic-textが自動管理）。

* 5. 実装上の技術的課題と対策 (懸念点とブラッシュアップ)
実際にコードを実装するにあたり、以下の5つの課題に対策を講じる必要がある。

** 5.1. 論理行と物理行のギャップ（Word Wrapへの対応）
現代のエディタ（VS Code, Zed等）において画面分割やドキュメント執筆のために自動折り返し（Word Wrap）は必須である。
- *課題*: Word Wrap 有効時、1つの論理行（改行コード基準）が複数の物理行（画面表示基準）に分割されるため、スクロール位置（ピクセル）から表示対象行を特定する $O(1)$ のクリッピング計算が破綻する。
- *対策*: Text Core と Layout Engine の中間に、論理行から物理行へのマッピング、および各行の高さ・幅をキャッシュするデータ構造（Layout Cache / B-Tree等）を構築する。バッファ変更時は、該当行とその周辺のみをインクリメンタルに更新する。

** 5.2. IME（日本語入力）のハンドリング
- *課題*: winit から送られる `WindowEvent::Ime`（Preedit / Commit）の処理が必要。確定前の文字列（プレエディット文字列）はまだ Rope バッファに存在しないため、描画時のみ一時的にインライン挿入してレイアウト計算と下線描画を行う必要がある。
- *対策*: Layout Engine に対し、「現在IME入力中のテンポラリな文字列と、その装飾（変換中の下線等）」をシームレスに受け入れて一時描画命令に変換する設計をはじめから組み込む。

** 5.3. シンタックスハイライトの非同期化
- *課題*: イベントループの Layout フェーズで毎回 `syntect` 等の解析を走らせると、巨大なファイルや複雑なコードのタイピング時に遅延（レイテンシ）が発生する。
- *対策*: ハイライトのパースはメインのイベントループ（UIスレッド）ではなく、バックグラウンドスレッドで非同期に実行する。
  - メインスレッドはタイピングされた文字を即座に Rope に反映し、プレーンテキスト（または古い色情報）で超高速に描画。
  - 裏でパースが完了したタイミングで色情報をUIスレッドに送り、画面を再描画（リリクエスト）する。必要に応じて差分パースが得意な `tree-sitter` の採用も検討。

** 5.4. 座標変換とヒットテスト (Hit Testing)
- *課題*: マウスによるカーソル移動やドラッグ選択の実装には、ピクセル座標からテキストのインデックスを逆引きする仕組みが必要。
- *対策*: cosmic-text のレイアウト済みバッファに対する座標逆引き機能を利用する。その際、Viewportのスクロール量（`scroll_x`, `scroll_y`）や、行番号表示領域のオフセット幅を差し引いた「エディタ内の相対座標」に変換してから渡すレイヤを設ける。

** 5.5. Vello の不採用判断と将来への備え
- *判断*: 本プロジェクトでは現時点において Vello を採用しない。
- *理由*:
  1. カーソル矩形・選択ハイライト・波線といった描画対象はすべて単純な矩形・線分であり、ベジェ曲線を扱う Vello は over-spec である。
  2. Vello は内部で wgpu デバイス・キューを自前で初期化しようとする設計であり、既存の wgpu インスタンスとの共存には専用の初期化パスが必要となる。このコストは初期フェーズに対して高すぎる。
  3. Vello に割り当てていた役割（カーソル・選択・図形）はすべて ~renderer/shape.rs~ で素の wgpu により代替できる。
- *将来の部分導入について*: ミニマップや SVG アイコン等、真にベクターグラフィックスが必要な場面が生じた際は、レンダーパスを分離した設計（§ 5.6 参照）により追加コストを低く抑えた状態で再検討する。

** 5.6. レンダーパス分離方針（将来の拡張性確保）
各フレームの描画は、役割ごとに独立したレンダーパスを順番に呼び出す構造とする。

#+BEGIN_SRC plaintext
Frame N:
  Pass 1: wgpu → 背景・カーソル矩形・選択ハイライト  (renderer/shape.rs)
  Pass 2: wgpu → テキスト描画 (renderer/text.rs)     ← 将来追加
  Pass 3: ???  → ミニマップ等のベクター要素           ← 必要になった時点で検討
#+END_SRC

- 各パスは ~renderer/mod.rs~ の ~render()~ メソッド内で順番に呼び出されるだけであり、互いに独立している。
- 将来 Pass 3 を追加する際も既存のパスに手を入れる必要がなく、追加コストを最小に抑えられる。
- ~RenderPass~ を途中で中断して別ライブラリに渡す設計（パス混在）は行わない。

* 6. ディレクトリ・モジュール構成案
#+BEGIN_SRC plaintext
src/
├── main.rs            # winitのイベントループ起動、wgpuの初期化
├── app.rs             # アプリケーション全体のステート管理（ウィンドウとエディタの紐付け）
├── editor/

│   ├── buffer.rs      # ropey を使ったテキストバッファ管理

└── renderer/
    ├── mod.rs         # wgpu のデバイス、キュー、レンダーパスの管理
    ├── text.rs        # cosmic-text のインテグレーション（文字レイアウト・カラー適用）
    └── shape.rs       # wgpu を使ったカーソル（矩形）や選択ハイライトの描画
#+END_SRC

* 7. ファーストステップ：単一カーソルの表示と移動 (開発の第一歩)
プレーンテキストを表示する前段階として、「カーソルを画面にレンダリングし、それをキー入力で動かす」ことを最初の目標とする。これにより、「OSイベント（winit） → 内部状態更新（Model） → 画面描画（wgpu）」のパイプラインを最小構成で開通させる。

** 7.1. カーソルのデータ構造 (Model)
テキストバッファが存在しない（空のバッファ）状態でも破綻しないよう、グリッドやピクセルではなく、将来的なバッファ対応を見据えて「文字のインデックス（バイトオフセット）」を基準に管理する。

~Cursor~ 構造体はデータ層（~editor/~）に属するため、レンダリング座標（ピクセル値）は持たない。~screen_x~ / ~screen_y~ はフォントサイズ・スクロール位置・ウィンドウサイズに依存する「描画の都合」であり、レンダラー側（~renderer/~）がフレームごとに算出する責務を持つ。

#+BEGIN_SRC rust
struct Cursor {
    position: usize, // テキストバッファ内における現在のバイトオフセット位置（初期値は0）
}
#+END_SRC

ピクセル座標への変換は ~renderer/shape.rs~ が担い、現フェーズでは固定値（例: x=8.0, y=8.0）から開始する。~cosmic-text~ 導入後はレイアウト結果から自動算出する。

** 7.2. イベントループでの処理フロー (Controller)
1. *`WindowEvent::KeyboardInput` の検知*: 矢印キー（`KeyDown`）の押下を検知。
2. *内部状態の更新 (Update)*: 左矢印なら `position` をデクリメント（最小値0）、右矢印ならインクリメント。状態変更トリガー（再描画フラグ）を立てる。
3. *再描画の要求*: `window.request_redraw()` を呼び出し、GPU描画フェーズをキックする。

** 7.3. レンダリングパイプライン (View)
- *wgpuによる矩形描画*: 最初は文字がないため、カーソルは純粋な「1つの長方形（矩形）」として描画する。4つの頂点（Vertex）データを用意し、インデックスバッファで結んで長方形を作成する。
- *座標系の正規化*: wgpu標準の NDC（Normalized Device Coordinates）から、ウィンドウのピクセルサイズ（例: 800x600）を直感的に扱えるよう、シェーダー（WGSL）側へ正射影行列（Orthographic Projection）を渡す設計にする。
- *動作テスト*: カーソルのサイズ（幅 2px、高さ 16px 等）を固定値で定義し、キー入力をトリガーにX座標が `+10px` ずつズレていくような簡易的な描画テストから着手する。
