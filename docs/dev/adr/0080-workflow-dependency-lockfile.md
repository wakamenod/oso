# 0080. Workflow dependency lockfile

- Status: Proposed
- Date: 2026-11-08

## Context

[ADR 0021](0021-development-tooling.md) pins every third-party action in the workflows by
commit SHA, with a version comment, as tags can be moved by an action's owner. That pins
only what a workflow names. An action that calls other actions, such as a composite
action, runs whatever those references resolve to on the day, and nothing stops a run if
a reference no longer points where it did.

GitHub Actions workflow lockfiles became generally available on 2026-10-28, on the Free
plan as well. `.github/workflows/actions.lock`, generated by the `gh actions-lock` CLI
extension (`github/gh-actions-lock`), records the commit of every action a workflow's
steps use, the actions those actions use too, and the owner and repository ids behind
each name. Once a workflow is in the lockfile, a run uses the locked commits, and fails
before the step if a dependency has no pin or a pinned commit is no longer reachable from
its ref.

The CI also gained a local composite action, `.github/actions/install-just`, which uses
`actions/cache`. The extension does not follow `uses: ./…` paths. It migrates them to
`uses: $/…`, which runs the repository's own action at the workflow's commit and lets the
lockfile pin what that action uses.

## Decision

This amends [ADR 0021](0021-development-tooling.md): third-party actions are pinned by the
lockfile, not by SHAs in the workflow files.

- **Every workflow is in the lockfile.** `.github/workflows/actions.lock` is generated with
  `gh actions-lock` from the repository root, and is never edited by hand.
- **Workflows name actions by their exact version tag** (`actions/checkout@v7.0.1`), as the
  extension writes them. The lockfile holds the commit each tag had when it was locked, and
  a run uses that commit even if the tag is moved later. When first generated, every locked
  commit was the one the workflows had pinned by SHA.
- **The repository setting "Require lockfile" is on** (Settings > Actions > Policies), so
  GitHub refuses to run a workflow that is not in the lockfile. A workflow can therefore not
  run unpinned by leaving it.
- **Local actions are referenced as `$/.github/actions/…`**, so what they use is locked.
- **A change to an action dependency regenerates the lockfile in the same commit.** A diff
  in which an `owner_id` or `repo_id` changes is investigated before it is merged.
- **The lockfile, like the rest of `.github/`, is a file that defines the checks**, and
  changes to it follow the same approval ([AGENTS.md](../../../AGENTS.md)).
- **Tools downloaded by a step** (just, gitleaks, cargo-deny and the others) are not
  actions, so the lockfile does not cover them. They keep their pinned checksums.

## Consequences

- Actions called by other actions are pinned, and a moved or rewritten reference stops the
  run instead of running something else.
- Updating an action means running `gh actions-lock` again. Writing the lockfile needs the
  `workflow` scope, which pushes from the author's machine have.
- "Require lockfile" is a repository setting, not a file, so it is turned on by hand once
  this lands, and a fork or a copy of the repository does not have it.
- Version tags make the workflows easier to read and to update than SHAs.

## Alternatives considered

- **SHA pins in the workflows as well as the lockfile:** two records of the same commit,
  which the extension rewrites to tags, and which the lockfile may not match by name.
- **SHA pins alone, as before:** leaves the actions that actions call unpinned, and nothing
  stops a run whose reference has moved.
- **Verifying the lockfile in CI with `gh actions-lock --verify`:** would download the
  extension in every run, and GitHub already refuses a run whose dependencies are not
  locked.
