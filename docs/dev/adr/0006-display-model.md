# 0006. Layered display model and decorations

- Status: Accepted
- Date: 2026-11-03

## Context

Git status buffers, directory listings and org documents rely on attaching
data to text, folding, virtual text and generated buffers. If M1 assumes
"one buffer line = one screen row", everything has to be rebuilt later. See
[`display-model.md`](../display-model.md).

## Decision

- **Transform pipeline in `oso-core`:**
  - buffer → FoldMap → InlayMap → TabMap → WrapMap → BlockMap → display rows
  - O(log n) mapping in both directions using summarized trees, as in Zed
- **Decorations are position-based layers owned by producers:** syntax,
  search, diagnostics, modes and selections.
  - Anchors shift with edits.
  - Layers can be replaced atomically from background threads.
  - Decorations do not travel with copied text.
- **Semantic decorations** carry typed data and an optional keymap at point.
- **Variable row heights** are supported in the architecture (inline images,
  larger headings, multi-row blocks). Rows are uniform by default.
- **Soft wrap is off by default**, enabled per mode or by toggle. `C-n` and
  `C-p` move by logical lines.
- **Buffer kinds:** file, generated (read-only, regenerated by its mode) and
  terminal ([ADR 0015](0015-terminal.md)).

## Consequences

- Git, directory and org features fit without reworking the display layer.
- Asynchronous highlighting is simple: swap a layer.
- More upfront work in M1 than a naive line renderer.

## Alternatives considered

- **Emacs-style text properties that travel with text:** familiar, but harder
  to combine with async highlighting and harder to manage.
- **Always-uniform row heights:** simpler, but rules out inline images and
  sized headings.
